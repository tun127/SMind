# 开发计划与发布节奏（2026-09-21 定稿）

> 依据：用户 2026-09-21 拍板的四条原则 + 仓库实况（`package.json` 现行 `0.9.1`；`docs/known-issues.md` 的 P0–P3 已全清、
> 仅剩 P4 分发与 P5 功能缺口；`docs/ops.md` 台账待办集中在 #3/#13/#14/#20）。
> 本文件回答两个问题：**什么该什么时候修/做**，以及**每次发版必须走完哪些动作**。

---

## 零、四条原则（用户拍板，本计划的地基）

1. **大 bug 马上修**
2. **小 bug**：一周一修 或 一月一修
3. **小型功能更新**：一月一更 或 一季一更
4. **大型功能更新**：季度 或 半年

---

## 一、严重度分级与响应时限（把原则 1/2 变成可判定、可追责的规则）

| 级别                      | 判据（满足任一即入级）                                               | 响应时限                   | 发布方式                                    |
| ------------------------- | -------------------------------------------------------------------- | -------------------------- | ------------------------------------------- |
| **P0** 数据 / 启动 / 收入 | 丢数据；崩溃；打不开或存不了；装不上；许可码失效；自动更新把用户搞挂 | **立即开工，48h 内出补丁** | hotfix：`0.9.x`（**跳过列车**，先修再复盘） |
| **P1** 安全 / 合规 / 渠道 | 安全绕过；许可可伪造；CSP 或权限回归；无法发码 / 无法退款            | **72h**                    | 随最近列车，或并入 hotfix                   |
| **P2** 功能异常但可绕过   | 有 workaround 的功能错误；可见性能回归；导出内容不对                 | 进**周更窗口**             | 周更 patch（攒 1–3 条一起发）               |
| **P3** 体验 / 文案 / 样式 | 错位、错别字、图标、颜色                                             | 进**月度版**               | 月度                                        |

**定级判据（防争议）**：受影响用户数 × 是否伤数据。**有争议时按更高一级处理**（宁可多修一次）。
反向约束：**不得把 P2 当 P0 插队**（会打断所有排期，且"狼来了"会让真 P0 提速失效）。

---

## 二、功能分级（把原则 3/4 变成可排期的规则）

| 级别     | 判据                                   | 节奏                | 前置门槛                                     |
| -------- | -------------------------------------- | ------------------- | -------------------------------------------- |
| **小型** | ≤ 2 人日；单模块；不碰数据层与布局核心 | **月度**（每 4 周） | 无                                           |
| **中型** | 3–10 人日；跨 2–3 模块；需要回归验证   | **季度**            | 一页设计说明（改什么 / 为什么 / 怎么验收）   |
| **大型** | 新平台、新格式、架构级改动、主线新能力 | **季度或半年**      | RFC：目标 + **非目标** + 验收标准 + 回滚方案 |

**两条铁律**

1. **修 bug 优先于新功能**：列车到点时，若 P0/P1/P2 未清，功能版延后（bug 不延后）。
2. **大型功能必须有"用户证据"**：≥5 条明确用户请求，或访谈/数据支撑，否则不进排期（避免自我感动式开发）。

---

## 三、发布列车（固定节奏，明确"什么时候发"）

| 列车               | 频率                             | 装什么        | 备注                       |
| ------------------ | -------------------------------- | ------------- | -------------------------- |
| **hotfix**         | 随时（不受约束）                 | P0 / P1       | 唯一可以打断别的事的       |
| **周更**           | 每周一天（**待你定，建议周五**） | P2 级 bug     | 当周无单则不发，不硬凑版本 |
| **月度**           | 每月一次                         | P3 + 小型功能 | 版本号进 `0.10`、`0.11`…   |
| **季度**           | 1 / 4 / 7 / 10 月                | 中型功能      | 提前两周冻结改动，只修回归 |
| **半年（大版本）** | 视 RFC 而定                      | 大型功能      | `1.0` 门槛见第四节         |

**保底承诺（与 Pro 的 1 年更新保障绑定）**：**任意两次可交付版本之间不超过 90 天**。
—— 即：哪怕当季没有新功能，也发一个 patch/维护版。**不承诺"永久更新"**（对外口径见 `phase3-plan.md`）。

---

## 四、版本号规则

- `0.9.x` —— **修复线**：只有 bug 修复，不含新功能
- `0.10`、`0.11` … —— **月度小功能线**
- `1.0` —— **大型里程碑**，够格条件（建议，三条同时满足）：
  1. 至少一项大型能力落地（如 macOS 版、文档加密、多语言）
  2. 连续 3 个月无 P0
  3. 有一批真实用户与访谈数据（对应台账 #16）
- 需要试用的大功能用预发布号：`x.y.0-beta.N`

## 五、近期排期（具体到版本与内容）

### `0.9.2`（本周–下周｜修复线｜最高优先）

1. **更新源从 GitHub 切回 `dl.smindapp.cn`**（`electron-builder.yml`，台账 #3 的前置）
2. **自动更新真机首跑验证**（台账 #3）→ **测试方案：`docs/auto-update-test-plan.md`**（两阶段 + 14 条用例）
3. **两处随带修复**（测试方案 §2 读代码发现，均属本功能自身）：①「已是最新版」判定误用 `version !== current`
   → 渠道版本 ≤ 本机时会谎报"发现新版本 v旧版"（源码已确证，P2 级）；② updater 用 `console` 打日志，
   而 `log.ts` 只写显式 `logMain` → **打包版里自动更新的日志没有任何落点**，静默失败将无法诊断
4. 随带：期间收到的 P2 级 bug；`README.md` 已知限制复查
5. 不装任何新功能（修复线只修 bug）

### `0.9.3`（月内｜修复线）

  —— 现状只能读不能建（详见 `known-issues.md` 的 2026-09-22 登记：全仓无任何写入 `detachedChildren` 的路径）；

## 六、每次发版的固定动作（Release Checklist，不许跳）

1. **五道门槛全绿**：`typecheck` / `lint` / `format:check` / `selfcheck` / `verify`
2. `npm run dist` 产包 → **本机装一次冒烟**（不是只看构建成功）
3. `CHANGELOG.md`：改了什么 / 影响谁 / 怎么回退
4. Release 四件资产齐全 + `latest.yml` 版本号正确（**"发版了但 latest.yml 没更新"= 自动更新静默失效**）
5. 上传国内镜像 → 实测 200/206 与 `content-length` 一致
6. 官网版本号、下载直链、下载页镜像探测复测
7. 台账 `docs/ops.md` 更新状态（**价格 / 发货方式 / 免费边界 / 退款条款的文案不动** —— 红线）
8. **每个 bug 修复补一条自检断言**（自检数只增不减：当前 2753）

---

## 七、需要你拍板的三件

1. **周更窗口定在哪天**（建议**周五**）
2. **版本号是否按上表**（`0.9.x` 修复线 → `0.10` 小功能 → `1.0` 只给大型里程碑）
3. **`0.10` 的那个小功能选哪个**：自动编号 / FreeMind `.mm` 导入 / 纯文本大纲导入
