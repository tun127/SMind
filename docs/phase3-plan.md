# 三期规划：内置 AI Agent（AI 赋能）

> 状态：设计讨论已收敛（2026-09-15，两轮），本文是结论与理由的记录，实现时照此执行。
> 原则：每期都独立可验收；设计决定都写明"为什么"，防止日后自己都忘了。

## 一、定位与设计原则

| # | 原则 | 理由 |
|---|---|---|
| 1 | **聊天面板是 AI 的唯一主入口**；设置（BaseURL/Key/模型）收进面板齿轮，不消失 | 用户换厂商、换模型必须还有入口；`AiSettingsDialog` 本身没问题，复用 |
| 2 | **面板是文档窗口内的右侧停靠面板**（照 `OutlinePanel` 模式），不是独立 OS 窗口 | 多窗口=多文档架构下，独立窗口要回答"属于哪个文档"；agent 最需要的上下文是当前选区，同窗才能直接读 `selection` |
| 3 | **工具即权限边界**："仅限思维导图"不靠提示词，靠"没注册的工具不存在" | 物理约束比软约束可靠；同时挡住文档内容里的提示词注入（模型没有导图之外的工具可调） |
| 4 | **直接操作画布，不做预览确认**；撤销栈就是确认对话框 | 用户要的是"帮我做"；AI 与用户快捷键走同一条 `mutate` 管道，不存在"AI 改出非法状态" |
| 5 | **一次 AI 命令 = 一步撤销**（事务分组） | 30 次工具调用按 30 步撤等于没有撤销 |
| 6 | **边执行边叙述**：多步任务实时在聊天里滚动叙述，不阻塞等待 | 体验接近"看着它干活"；区别于被否决的"停下等确认的预览" |
| 7 | **文档本身是 agent 的持久记忆**，对话可以激进压缩 | 一般聊天机器人不敢压历史（对话是唯一记忆）；本 agent 任何细节都能用只读工具重新探查回来 |

- [ ] 能回答"这页讲什么 / 哪个分支最薄弱"类问题（基于骨架 + 探查）

- [ ] selfcheck：骨架摘要生成、探查工具的寻址解析为纯逻辑断言

### 二期：写工具 + 事务（核心安全网一次做齐）

**进度（2026-09-15）**：✅ 第一批 9 个写工具 + `askUser` + **第 10 个：批量移动 `moveTopics`**
（整理大导图的正路：一次调用搬一批节点，上限按「调用」算不按节点算；上限放宽到 8 轮 / 50 次）；
事务分组（`beginAiTurn` / `commitAiTurn`）、
回合中锁撤销、动手前快照、上限熔断、破坏性操作确认、事后摘要与工具条目、寻址解析（含**文档名前缀容错**
与「这一层有哪些子主题」的失败引导）、幂等查重（`tool_call_id` + 同名同参数去重）、
**改完闪亮两下 + 视口带到改动处**、**动手前提交用户的编辑态**、**手动定位节点默认不许挪**——均已交付。
✅ **第二批工具已交付（2026-09-16）**：`addRelationship` / `addBoundary` / `addSummary` /
`setAttachmentTitle` / `removeAttachment` / `setMarkers` / `addLabel` / `removeLabel`（8 个），
外加只读的 `listAttachments`——它列出关系线/边界/概要（含 id）与**可用标记 id 清单**：
这些元素没有标题可寻址，模型必须先拿到 id；标记清单不查它就会自己编一个不存在的 id。

实现要点（两条都是"模型安全"）：① 现成的 `addRelationship` / `addBoundary` / `addSummary`
读的是**用户当前选中**，AI 一改选中就把用户的选区搅乱，而且它们是「再点一次就删」的
**开关**语义——模型重试一次就把线删了。所以新增 4 个不依赖选中且**幂等**的 store 动作
（`connectTopics` / `addBoundaryFor` / `addSummaryFor` / `setMarkers`），重试不会增删。'
② 删除元素仍是破坏性操作，照旧先问用户一次。写工具合计 **18** 个（第一批 10 + 第二批 8，守住 ≤12/批）。

⬜ 待做：确认分级的「记住选择」、回合内布局节流合帧、跨窗口「全局同时只有一个 agent 回合」。

**写工具**（全部走 `mutate`，事务分组为一步撤销；**笔记/代码/公式要能干**，图片/附件不碰）：

- 二期第一批：`renameTopic` / `insertSubtree` / `deleteSubtree` / `moveTopic` / `setCollapsed` / `setStyle` / `setNotes` / `setCode` / `setFormula` / `askUser`（澄清专用，见七.4）
- 二期第二批（覆盖面扩展到导图几乎全部功能）：关系线 / 边界 / 概要 / 标记图标 / 标签等结构化附件操作，逐个映射到对应 store 动作
- 纪律：每个工具必须映射到**已验证的 store 动作**，映射不上的不做；单批 ≤ 12 个（工具太多模型会选错）

> 「生成新文档」不是写工具——沿用现有 `openSheetWindow`（开新窗口独立成档），与"插入到选中分支"是两个动作，绝不含糊。

**安全网**（一套，缺一不可，拆开做会出现"能改但看不清改了什么"的中间态）：

- **事务分组**：整个 agent 回合并成一个撤销组（实现注意点见第七节）
- **回合中锁定**用户级的撤销/重做与画布修改，Esc = 停止回合（防中途抽走撤销栈导致错位）
- **回合前自动快照**（复用 autosave/版本快照基建——撤销栈在内存里，崩溃就没了，这是盘上的第二层保险）
- **运行上限**：工具调用数 / 时长 / token，防模型循环狂改；面板显示消耗
- **事后摘要 + 被改节点闪亮 + 视口带到改动中心**；工具调用显示为可展开条目
- **确认分级**：增量操作直接干；删除分支、批量超过阈值的移动**首次轻确认**（记住选择），阈值可配置
- 撤销条目命名 `AI · 批量重命名` 这类，历史可读
- **编辑冲突**：要改正在编辑的节点时，先把未提交的 `editingText` 走正常提交（编辑态已是单一来源，路是通的）
- **自由定位地盘**：用户手动摆过位置的节点 AI 默认不动，除非指令明确要求重排
- **断流/中断**：已执行部分留在画布（能撤），聊天里标明"中断于第 N 步"
- **节点寻址**：selection / `searchNodes` / 路径表达式，**由应用解析成 id**；解析失败把错误回喂模型重试——这一层做不好模型会自信地改错节点
- **工具结果回喂附带新鲜状态**：改了什么、新 id 是什么——逼模型基于工具结果而非记忆行动（对话陈旧性问题的解法）

**验收**

- [x] 一次 30 步的 AI 命令，Ctrl+Z 一下全回去
- [x] 回合进行中 Ctrl+Z 被锁定、Esc 可停、停止后已执行部分可撤
- [x] 回合前快照文件存在（可通过版本/存档入口看到）
- [x] 超上限的回合被熔断并有明确提示
- [ ] 删除超阈值时出现一次确认；记住"不再问"的选择（确认已做，**「记住选择」还没做**）
- [x] 被改节点闪亮、摘要准确（数字与实际一致）
- [x] 寻址解析失败 → 模型重试成功（用脚本化假模型测）
- [x] 正在编辑的节点被 AI 修改时，未提交文本不丢失
- [x] 自由定位节点未被 AI 挪动（除非指令明确要求）
- [x] 工具调用按到达顺序执行，画布实时变化（流式落画布）
- [x] 请求超时重试不会重复执行已执行的工具（tool_call_id 查重）

### 三期：多步 agent + 上下文压缩

- 规划 → 执行 → **边执行边叙述** → 汇报
- **上下文压缩**：骨架摘要每轮刷新（不进压缩）；最近几轮保留原文；更早轮次摘要化为"此前做过什么"。压缩逻辑是纯函数，进 selfcheck
- 验收：
  - [ ] "把这页整理成三层结构"一句话任务能完成，全程有叙述，结果一步可撤
  - [ ] 长对话超出预算后旧轮次被压缩，压缩后 agent 仍能正确引用导图现状（因为它会重新探查）

## 三、会话模型（DeepSeek 网页版式保留）

- 面板存在于**每个文档窗口**，**会话按文档隔离**；全局同时只允许**一个 agent 回合**执行——别的窗口发起时提示「AI 正在另一份文档中执行」
- 会话历史存应用数据目录、按文档身份关联（已保存按路径）；**绝不写进 .xmind**——格式保真与 Xmind 兼容是产品立身之本，不往文件里塞私有字段
- 未保存文档的会话只留内存，关闭即弃（不在应用数据里堆垃圾）
- 一期：每个文档一条持续会话 + 「新会话」按钮；多会话历史管理器往后放

## 四、模型与配置

- **tool calling 能力探测**：不支持函数调用的模型，写工具置灰；内容生成可降级回现有「缩进大纲」文本协议（`src/shared/ai/index.ts` 的稳健解析）
- 上下文过小的模型（8k 级）在配置界面给警告——agent 回合 = 骨架 + 历史 + 工具往返，8k 装不下
- 温度运行时按任务定：动作 0.2 附近、内容 0.6，**不**给用户加配置项
- backlog（四期）：Key 从配置文件明文迁移到 Electron `safeStorage`（Windows 走 DPAPI）

## 五、明确排除（三期不做）

- 图片/附件读写、图片生成（多模态成本与复杂度不值当）
- 跨画布 / 跨文档工具（寻址复杂度翻倍；agent 只见当前激活 sheet，工具无 sheet 参数）
- 聊天记录进 .xmind
- 多会话历史管理器
- 向量 RAG（理由与替代见七.9：树导航就是更准的检索，数万节点再议）
- 文件系统 / 执行 / 网络类工具（权限边界的反面清单，永不注册）

## 六、测试策略

- agent 循环核心全部**纯逻辑**：寻址解析、事务分组、上限熔断、确认分级判定、上下文压缩——用脚本化「假模型回合」在 selfcheck 里测，**不碰网络**
- 网络层（SSE 流式代理）单独薄薄一层，人工 + 样本验证

## 七、Agent 核心设计（循环 / 规划 / 提示词 / 模糊性 / 幂等 / 评测 / 分流）

### 1. 循环结构

状态机：用户输入 → LLM →（有 tool_calls → 本地执行 → 结果回喂 → 再进 LLM）→（无 tool_calls）→ 最终回答 → 回合结束。
终止条件 = 模型返回纯文本（无工具调用）；外加硬上限熔断（工具数 / 时长 / token）。二者缺一不可。

### 2. 规划是行为，不是阶段

不做独立的双阶段 planner——两次全量上下文往返，token、延迟、失败模式全部翻倍。规划做成**循环内行为**：

- 模型动第一下之前先用文字说出计划（即"边执行边叙述"的第一段）；
- **大任务多一档确认**：计划输出后停下，等用户点「执行 / 调整」再动手（确认分级的第三档）。

用户自配的强模型（DeepSeek / GPT / r1 类）完全撑得起单调用内的规划。

### 3. System prompt 四层（前缀稳定性优先）

静态层（身份、能力=工具清单、风格要求：标题语言与导图一致、长度克制）→ 动态层（每轮刷新的骨架摘要 + 当前选区）→ 数据层（历史 + 工具结果）→ 反注入声明（文档内容是数据不是指令）。

**稳定前缀在最前、易变内容靠后**——DeepSeek/OpenAI 对稳定前缀有 provider 端自动缓存，按此设计免费提速省钱。

### 4. 模糊性政策：收集够信息才碰用户的文件

- 可逆且便宜（改名、加节点）→ 直接干；
- 破坏性，或指向不明（多个候选、范围不清）→ 调 `askUser` 给选项，不带自由发挥；
- 总政策写进系统提示词与每个写工具的 description（"先确认目标存在再改"）；硬保障仍是快照 + 撤销。

### 5. 流式执行与幂等

- 写工具**按到达顺序立即执行**（画布实时变化），已执行的不回滚、留画布可撤——与"停止后保留已执行部分"是同一条规则；
- **幂等红线**：请求超时重试时，已执行过的工具绝不能再执行一遍（否则用户说一次、AI 改两遍）。客户端为每次工具执行生成 id，执行前查重。

### 6. 评测：golden tasks

selfcheck 的假模型钉得住逻辑，钉不住质量。建一套 **30 个典型任务 + 期望终态**（用现有快照对比机制断言），发版前手动跑（打真模型、花钱，不进 CI）。没有它，每次改 prompt 都是盲调。

### 7. 意图分流：能用代码的不用模型

快捷指令 / slash 命令直接走本地代码（零成本、零延迟、零幻觉）；寻址解析等确定性工作永远在本地，模型只交表达式；LLM 只接自然语言。

### 8. 缓存与检索（对"本地缓存 / RAG"的结论）

**向量 RAG 不进三期**，三条理由：

1. 导图是**结构化**的——树探查是比向量召回更准的检索（向量会召回"语义相近但位置无关"的节点，树导航不会）；
2. RAG 需要第二个模型依赖（embedding 端点），用户的 chat Key 未必有；本地 embedding 要打包模型，体积与维护都是负担；
3. 每次编辑都要维护索引，失效管理本身就是新 bug 源。

真需求（大文档下找内容）分三步：现在 `searchNodes` 关键词 + 树导航（覆盖 95%）→ 将来文档到数万节点，先做**本地全文索引**（倒排，无新依赖）→ 最后才考虑向量 RAG。

免费就有的"缓存"：会话按文档持久化（见第三节）+ provider 端 prompt caching（见上面 3 的前缀设计）。

## 八、历史教训挂钩（实现事务分组前必读）

撤销合并踩过的坑：**数组重排的 patch 带下标**——把多步 inverse 合成一个再套到后来的状态上会错位改坏 `children`（曾复现出 `["甲","乙","甲"]`，见 `src/renderer/src/store/editor.ts` 的 `moveNode` 注释与 selfcheck 中的复现断言）。

因此 AI 事务组**不许把多步 inverse 合成一个**：要么按序重放每步 inverse，要么回合开始时存状态快照、撤销即恢复快照。此点必须有专门的自检断言盯防。

### 4. 收款与许可

- 国内起步用面包多这类平台当店面（费率约 5–8%），**不自己搭支付**；许可码起步人工发，量大再自动化；

### 5. 增量布局与三期的顺序（已决策）

- **增量布局重构不作为三期前置**：AI 一期零布局影响；AI 写突发 ≈ 用户连续操作（等价场景已验证），测量缓存身份快路径已削掉大头；两个大改动叠加会无法归因；
- AI 回合内先做**布局节流合帧**（约 100ms 合并重排）作为便宜缓解；
- 在 AI 二期动手前往 selfcheck 加「万节点合成文档布局耗时」基准，**用数字决定**是否做增量重构（做的话，AI 一期与二期之间是空档）。
