## 1. 为什么**不能**拿线上 0.9.1 来验 0.9.2 的新更新源

更新源写在**打包产物**里（`resources/app-update.yml` ← 由 `electron-builder.yml` 的 `publish.url` 生成）：

- 已发布的 0.9.1 里烧进去的是 **GitHub 直链**，你改不了它 → 拿它永远验不到 OSS 源；
- 本次要验的恰恰是"**换成 `https://dl.smindapp.cn/` 之后还通不通**"。

**所以必须：先装一个"带新源"的构建，再由渠道推一个版本号更高的版本给它。** 且版本号必须能让 semver 判定为"更新"
（`0.9.2-alpha.1` 收不到 `0.9.2-alpha.0`——预发布号更小，electron-updater 会判为"无更新"）。

## 2. 🔴 三条读代码得到的前置结论（其中 1 条是真 bug）

### 2.1 真 bug：「已是最新版」判定写成了「版本号不同」

`src/main/update/index.ts:130-133`：

```ts
const result = await autoUpdater.checkForUpdates()
const version = result?.updateInfo.version ?? null
const current = app.getVersion()
if (version !== null && version !== current) {  // ← 这里
```

**已从 `node_modules/electron-updater/out/AppUpdater.js` 确证**：`checkForUpdates()` 在**无可用更新**时
**不返回 `null`**，而是返回 `{ isUpdateAvailable: false, versionInfo, updateInfo }` ——
即 `result.updateInfo.version` 是**渠道上的版本号**，与"有没有更新"无关。

**后果**：当渠道版本 **≤** 本机版本时，会弹出

> 「发现新版本 **v0.9.0**（当前 v0.9.1）」+「正在后台下载…」（其实 never 会下载）

**什么时候会真的发生**：① 我们**回滚渠道版本**（更新出事故时撤回版本）而用户已装新版；
② 本机测试构建版本号高于渠道（**测试期几乎必然**）；③ 用户手动装回旧版 ← → 这种是正常升级。

**修法（3 行）**：改用 `result?.isUpdateAvailable` 作为判据（`false` 或无 `versionInfo` → 显示"已经是最新版"）。

### 2.2 自动更新的日志**进不了日志文件** → 静默失败将无法诊断

`src/main/log.ts` 只写显式调用 `logMain(...)` 的内容；而 `update/index.ts` 用的是：

```ts
autoUpdater.logger = console // :73
console.log('[updater] 免安装版：跳过…') // :67
console.warn('[updater]', error.message) // :81
```

打包版**没有终端**（用户双击启动），`console` 输出**没有任何落点** → 例行检查失败是静默的（设计如此），
而它连日志都没有 → **一旦真机首跑失败，我们手上就没有任何证据**。

**修法（约 6 行）**：把 `autoUpdater.logger` 换成写 `logMain('updater', …)` 的适配器（`info/debug/warn/error` 四个方法），
并把那两处 `console.*` 一起改成 `logMain`。**这条不改，本方案有一半用例无法取证。**

### 2.3 差分下载需要渠道上**同时有旧版本的 blockmap**

`electron-updater/out/providers/Provider.js:22-25`：

```js
getBlockMapFiles(baseUrl, oldVersion, newVersion, …) {
  const newBlockMapUrl = …`${baseUrl.pathname}.blockmap`
  const oldBlockMapUrl = …`${baseUrl.pathname.replace(newVersion → oldVersion)}.blockmap`
```

即差分要 **新包的 blockmap + 当前已装版本 exe 的 blockmap 同目录可下载**。
0.9.1 的 blockmap **不在 OSS 上**（在 GitHub）→ 换源后 **0.9.1 → 0.9.2 会退化为全量下载**（≈108 MB，不报错、只是慢）。

**建议**：把已有的 `SMind-0.9.1-x64-setup.exe.blockmap`（本地 `release/` 里有）一并传上 OSS 根目录 →
差分生效。**该项不是发版门槛**（全量下载也能更新成功），列为优化项。

## 3. 两阶段策略（关键设计：不往公开渠道放任何假版本）

| 阶段             | 装什么（源）                                      | 渠道放什么                               | 覆盖哪些用例                                   | 对外风险           |
| ---------------- | ------------------------------------------------- | ---------------------------------------- | ---------------------------------------------- | ------------------ |
| **一、本机回环** | `0.9.2-rt.1`（源 = `http://127.0.0.1:8099/`）     | 本机静态服务器放 `0.9.2-rt.2` 的四个资产 | T2–T4、T6–T10、T12–T14（含**全部破坏性用例**） | **零**（不出本机） |
| **二、真渠道**   | `0.9.2-rt.3`（源 = `https://dl.smindapp.cn/`） | **真 0.9.2**（正常发版）                 | T1、T5（真机首跑 + 真域名 + 真差分/全量）      | 极低（见下）       |

**为什么阶段二不用造假版本**：`0.9.2-rt.3` **只安装、从不上传**；渠道里从头到尾只有
`0.9.1`（GitHub）与 `0.9.2`（OSS）两个真版本 → **渠道零污染** ✓
且真 0.9.2 先上传、后宣布，中间的窗口里唯一跑着"OSS 源"的机器就是测试机 ✓
（**附带收益**：这一步同时在"对外宣布之前"暴露问题，比宣布后再发现强得多。）

**版本号安排（2026-09-21 修订：改成单调递增，避免"降级安装"的歧义）**

```
阶段一（本机）：装 0.9.2-rt.1（源=本机 8099）  →  渠道给 0.9.2-rt.2
阶段二（真源）：装 0.9.2-rt.3（源=OSS，D3 重打包）→  渠道给真 0.9.2（D4 发版）
收尾：        本机已是 0.9.2 ✓

单调递增的好处：rt.1 < rt.2 < rt.3 < 0.9.2，全程不需要卸载重装，
也不会出现"安装器遇到降级版本号"这类与本次验证无关的干扰。
所有 rt.* 资产**只在本机服务器/只被安装，从不上传**到 OSS 或 GitHub。
```

> 由 `http://` 的可行性：`GenericProvider` 只做 `newBaseUrl(url)` + `httpRequest`，
> **源码里没有 https 强制**（已核）；若实测被拒，退路是自签证书 + `NODE_EXTRA_CA_CERTS`，如实记录即可。

## 7. 回滚方案

## 8. 红线

- **绝不覆盖或删除线上 0.9.1 的四个资产**（官网回退直链与老用户的渠道都靠它）
- 不动价格 / 发货方式 / 免费边界 / 退款条款文案
- 不动许可（激活/验签）链路；不动 `shared/update-policy.ts` 的既有判据**语义**
  （portable / 6 小时 / releaseNotes 清洗）。
  **已批准的受控例外（2026-09-21）**：`shouldRecheck(lastCheckAt === null, …)` 的 null 分支
  —— 原来「没查过」被当成「该查」，使窗口聚焦在启动 ≈1 秒时抢跑一次检查（D-15 / T3）。
  三条语义一行未改，且由三条断言钉住（null → false / 差 1ms → false / 满 6h → true）。
- 每修一条 bug **补一条自检断言**（自检数只增不减，现 2753）
- 测试构建的版本号**一律带 `-rt.N` / `-alpha.N`**，且**从不上传**

## 补记：T7 的机制已静态确证（2026-09-21，读源码 + 最小 harness）

上面那条"未从源码确证"现在有结论了 —— **实测仍需做（确认行为一致），但不必靠实测去猜机制**。

**证据一 · `node_modules/electron-updater/out/BaseUpdater.js:13-27`**

```js
quitAndInstall(isSilent, isForceRunAfter) {
  const isInstalled = this.install(...)   // ① 先起安装器（spawn NSIS）
  if (isInstalled) setImmediate(() => { …; this.app.quit() })   // ② 再 app.quit()
}
```

→ 用的是 `this.app.quit()`（**可被打断**），**不是** `app.exit()`。

**证据二 · 最小 harness**（`.tmp-check/t7-quit-semantics.cjs`，直接用 `electron` 跑，不需要安装包）：

```
--- 调用 app.quit()（等价于 quitAndInstall 内部那一步）---
BEFORE_QUIT
CLOSE_HANDLER_ASKED_AND_PREVENTED
STILL_ALIVE=true
CONCLUSION=退出被中止（保存确认有机会弹出）✅
```

→ `app.quit()` 先发 `before-quit`，再走每个窗口的 `close`；**`preventDefault()` 能中止退出**。

**对照我们的链路**：

1. 按钮路径 → `install()` 起安装器 → `app.quit()` → `lifecycle.ts` 的 `before-quit` 算 `windowsToAsk`、
   `preventDefault()` 并给每个窗口发 `IPC.closeRequest` → 渲染层弹「保存吗」；
2. 用户点**取消** → `closeCancel` 复位 → 窗口留着、**退出被中止、内容不丢** ✅；
3. 保存/不保存 → `confirmClose` → 窗口关完 → `approveQuit()` → 退出 → 安装器收尾安装并重启。

**结论：T7 的核心要求（"必须先弹保存吗、不许静默丢内容"）在结构上成立。**

⚠️ **一处顺序瑕疵，如实登记**：安装器在弹窗**之前**就已 spawn（① 先于 ②），用户取消后它会留在后台
等应用退出（NSIS 安装器会等待）。**不丢数据**，但不是最干净的行为。
若要彻底消除（按钮路径"先问后装"），有两个已确证的约束必须一起处理，否则会退化：
① `autoInstallOnAppQuit` 的 `onQuit` 路径用的是 `install(true, false)` —— 静默装且**不重启应用**，
所以"立即重启并安装"的语义只能由 `quitAndInstall()` 提供；② 因此"先问后装"必须在**全部窗口批准之后**
才调 `quitAndInstall()`，并在此期间**抑制 `window-all-closed → app.quit()`**，否则正常退出会先命中
`onQuit` 的静默装、丢掉重启语义。→ 属需要真机验证的改动，建议单独一批。

**方案方（2026-09-21）独立复核与判定**：

- **两处证据我都自己核过**：`BaseUpdater.js` 的 `quitAndInstall()` 确实是"先 `install(...)`、
  再 `setImmediate(() => this.app.quit())`"，且**没有 `app.exit()`、没有 `removeAllListeners`**
  （`BaseUpdater.js:21`）；那个 harness 用的是**真 Electron**（真 `BrowserWindow` + 真 `app.quit()`
  - 窗口 `close` 里 `preventDefault`），**不是自建 mock** → 结论可信。
    T7 因此从"要用真机去猜"升级为"**结构上成立 + 一条人眼确认**"。
- **补一条执行侧没提的推论**：`quitAndInstallCalled` 置位后，electron-updater 会忽略**后续**的
  `install()` 调用（`BaseUpdater.js:43-44` 的 `install call ignored`），但**已经 spawn 的安装器不受影响** →
  所以"用户点取消、随后正常退出"的很可能结果是：**照样装上，只是不自动重启**（不丢数据）。
- **T7 的人眼步骤收紧为"三看"**（原来只说"看对话框"）：
  1. 点「立即重启并安装」→ **必须立刻弹「保存吗」**；
  2. 点**取消** → 应用**不能退出**、内容**不能丢**；
  3. 顺手开任务管理器看有没有 `SMind-*.exe` 安装器进程在等 —— **有 = 上面那条推论成立**；
     若应用是被**强杀**（而不是弹窗后自退），**立刻上报**（那才是真问题）。
- **判定：这处瑕疵不修**（登记为 P3，进月度或永不）。三条理由：
  ① 它**不丢数据**（唯一要紧的事已成立）；② 修法要动 `window-all-closed → app.quit()` 与"退出批准"时序 ——
  正是**最容易丢数据**的那段链路，为一个后台进程去动它，风险大于收益；③ 触发场景罕见
  （用户先点「立即重启并安装」、再反悔点取消）。
